# Billing Module Context

Last reviewed: 2026-08-15
Status: Canonical module runtime; backend aliases are retired and the active imported-GCash page URL is documented below.

## Purpose and current scope

- Manage prepaid/postpaid plans and MikroTik profile bindings.
- Generate monthly billing entries, proration, balances, advances, and credit-limit state.
- Record, import, export, normalize, number, adjust, and delete payment entries.
- Produce payment history, breakdowns, receipts, account statements, and billing statements.
- Review customer payment confirmations and unmatched imports.
- Persist customer GCash proof submissions in JSON or MySQL, detect reused references and exact screenshot hashes, bind each imported transaction to one immutable allocation group of up to three distinct customer/current-month rows, and post every ledger credit/service restoration only after explicit Admin approval.
- Extract amount, reference, date/time, recipient, and transaction status from submitted GCash screenshots with local server-side Tesseract OCR, optionally supplement incomplete/low-confidence reads through an explicitly enabled OpenAI-compatible Vision AI endpoint, and retain field provenance plus normalized analysis as review metadata without allowing either analyzer to approve a payment.
- Import official password-protected GCash Transaction History PDFs and match pending proofs against credited reference/amount/date/recipient rows before Admin approval is allowed.
- Reconcile Payment History Excel imports against normalized official GCash references so exact one-to-three-account allocations bind once, existing ledger matches are linked without reinsertion, and amount/date/customer conflicts remain unposted for Admin review.
- Drive disconnection, keep-active, reconnection, and disconnected billing-policy workflows.

## Backend and APIs

- `backend/index.js` is the lazy module descriptor loaded by `server.js` through `core/runtime/module-loader`.
- Thirteen runtime entries plus internal complimentary/reconnection helpers, the GCash PDF/parser/history stores, `gcash-screenshot-parser.js`, and the provider-neutral `gcash-vision-ai.js` adapter live under `backend/`: plans, payments, records, confirmations, disconnections, scheduler, numbering, normalization, balance, refresh, profile, and queue/store helpers.
- The former thirteen repository-root backend shims were retired in Phase 11; consumers use canonical Billing paths or the module descriptor.
- `/api/plans`: plan CRUD through `backend/plans.js`.
- `/api/payments`: payment listing, entry, import/export, delete, and payment-link flows through `backend/payments.js`.
- `/api/payment-records`: account payment history and adjustments. Every record includes version 2 of the canonical backend-only `billingSummary` read model (`available`, `rows`, `context`, `currentCycle`, `nextCycleDate`, `billingStatus`, `dueDate`, `endingBalance`, `balance`, `advance`, and `reconciliation`). `nextCycleDate` is the next first day for prepaid and next month-end for postpaid.
- `PATCH /api/payment-records/:accountNumber/breakdown-adjustment` accepts an Admin-confirmed `planChange` with an effective month and required reason. The backend resolves the selected plan from the canonical plan store, owns plan amounts/categories, records the actor/time and previous plan, rejects direct client-authored `planChanges`, recalculates open cycles, protects paid cycles, and returns the subscriber synchronization result.
- The same adjustment endpoint accepts only an audited `complimentaryAccount` action with a current/future effective month, optional inclusive end month, required reason/confirmation, and Keep or current-month Write Off treatment for an existing balance. Direct browser-authored complimentary periods are rejected. Ending a period selects a later resume month so free months are never back-billed.
- `/api/payment-records` automatically assigns the oldest eligible Admin-approved queued referrals to the subscriber's latest generated unpaid billing month. A referral is eligible when its optional `applyFromMonth` is blank or is not later than that billing month. It applies at most two per month, never exceeds the remaining monthly charge, and carries every excess or future-scheduled referral forward without a queue limit. The adjustment endpoint accepts reasoned `referralApplication` reversals; manual application and browser-authored amounts are rejected.
- `/api/payment-records/reconciliation/report`: Admin branch-wide recalculation report for duplicate cycles, missing calculated charges, invalid advances/carry-over, missing current cycles, and ending-balance mismatches.
- Payment confirmation routers are mounted at shared confirmation queue paths.
- `POST /api/payment-confirmations/gcash-history/import` accepts an Admin-only raw PDF up to 8 MB plus its one-use password, parses every valid official transaction row, and stores normalized branch-scoped history without retaining the password or PDF bytes. Every normalized reference already present in the branch or earlier in the same upload is skipped without overwriting its stored details or stopping other new rows; the response reports imported, skipped-reference, conflicting-skipped, duplicate-file, and batch-recorded results. A repeated file with no new references is successful and does not add another batch record. `GET /api/payment-confirmations/gcash-history` returns the branch import/history view, including mapped recipient labels and each transaction's sanitized allocation when claimed. Queue reads include `gcashMatch`; GCash approval returns `GCASH_HISTORY_MATCH_REQUIRED` unless reference, incoming credit, exact amount, calendar date, and configured merchant recipient all match. Sender/customer-mobile mismatches remain visible and require human ownership verification.
- `POST /api/payment-confirmations/gcash-history/:reference/post-payment` is Admin-only and provides the explicit direct-import workflow. It accepts one to three distinct branch-account allocations with positive amounts plus the read-only imported amount and assignment confirmation; the browser does not select billing months. The server derives each account's canonical current cycle, payment status, and ending balance from the unchanged version-2 Payment Breakdown summary. Unpaid allocations remain capped by the positive amount due, while paid/settled or zero-balance current-cycle accounts accept the imported credit as an advance payment. Missing current cycles/balances, duplicate accounts, and totals that do not exactly equal the credit are rejected before the ledger payment is recorded on the current Manila posting date. It writes the whole group atomically in one JSON replacement or one MySQL transaction and finalizes one immutable assignment containing every current-month ledger entry. Historical breakdown rows and the canonical breakdown calculation are not edited. Duplicate ledger references, partial groups, amount changes, wrong-account reuse, and reassignments fail closed; a retry of the identical completed group returns the original entries. The legacy single-account request shape remains supported, but any supplied billing month is ignored in favor of the server-derived current month.
- `POST /api/payments/import-excel` normalizes each GCash reference against the branch's official imported history before writing. One to three distinct workbook customer rows may share one reference only when their total equals the incoming credit and every payment date matches the official transaction date. The server claims the official allocation before the JSON/MySQL ledger write and finalizes it with the imported entry IDs afterward. An exact payment already in Payment History is linked to the official row and skipped instead of inserted again; an already-posted identical allocation is idempotently skipped. Reserved, wrong-account, amount, date, direction, partial-group, and reused-reference conflicts do not write payments and are reported for Admin review. Manual binding of an unmatched imported row applies the same reference guard after the Admin selects the customer. Payment Breakdown calculations are unchanged.
- `PUT /api/payment-confirmations/gcash-history/:reference/remark` is Admin-only and updates only the imported row's classification metadata. Allowed categories are Expense — Unclassified, Operating Expense, Transfer, Refund, and Personal/Other; each save records the Admin identity and timestamp without changing the original reference, direction, amount, description, date, recipient, or allocation.
- GCash approval requires an explicit Admin customer-allocation confirmation, locks the originally submitted amount/reference, blocks reliable OCR contradictions, and atomically claims the imported reference for that submission/account before ledger posting. A conflicting claim returns `GCASH_TRANSACTION_ALREADY_ASSIGNED`; successful posting finalizes the allocation with the payment entry and reviewer audit.
- `/api/disconnections`: queue and service-policy decisions. `POST /api/disconnections/:accountNumber/reconnect` preserves the existing cycle for continue-billing disconnections; a stopped-billing account instead requires an Admin-confirmed, reasoned settlement with Keep, Write Off, or 2–24 month Installment treatment for the captured previous balance, Prorated Now, Full Month Now, or Next Regular Cycle for new billing, and Immediate or After Required Payment service activation. Both immediate-charge choices are rejected when the current month already has a generated regular bill.
- `/api/billing/run-once`: shared guarded billing trigger in `server.js`.
- Statement PDF and payment receipt handlers partly live in shared `server.js`.

All API prefixes and response contracts remain unchanged by the physical migration.

## Data and dependencies

- JSON is the default storage mode; optional relational paths use shared DB helpers.
- Prepaid accounts receive one idempotent monthly recurring charge on the first day of each Manila billing month; overdue prepaid cycles catch up in one scheduler run. Postpaid month-end scheduling is unchanged.
- A new postpaid customer's first mid-month activation period is calculated immediately as one prorated backend cycle. A payment recorded before the following postpaid month-end settles that activation cycle first; only an amount above the prorated charge becomes advance. Established postpaid recurring charges remain pending/view-only until the last day of the month.
- Multiple payments are credits against the existing monthly cycle. Excess credit becomes advance for the next cycle; deprecated per-payment `Prepaid renewal charge` debits remain in raw audit history but are excluded from effective balances and breakdown rows.
- When a disconnected account uses the Stop Billing policy, effective payments recorded after the final generated cycle settle that last frozen balance instead of being discarded or generating a new monthly bill. Partial payments leave the remainder unpaid, full payments settle it, and excess becomes advance.
- Effective-dated upgrades/downgrades are backend-owned. Unpaid cycles from the billing-effective month use the new canonical plan amount. Finalized paid rows retain their original amount and plan label; their prorated/full price difference is carried exactly once to the first open cycle as a separate debit or credit. The Billing adjustment store is the audit/history source, while Customer Management owns the subscriber's current plan and future scheduled snapshot. Current changes synchronize the resolved MikroTik profile immediately; future changes reuse the Billing scheduler's retry-safe scheduled profile application.
- Referral discounts are calculated only from active registry applications. Approval locks the entitlement without waiting for a referred-client payment. Billing creates exact-month automatic applications in FIFO order among records whose optional earliest `applyFromMonth` has arrived, at most two per cycle; unapplied and future-scheduled records remain queued indefinitely, and a reversed application skips its original month and returns to the later-month queue.
- Complimentary periods are stored in the branch/account Billing adjustment record. The scheduler advances prepaid first-of-month and postpaid month-end cycles without generating recurring charges for exempt months, while canonical rows retain any kept balance or apply the captured write-off once without creating advance. Active complimentary accounts stay service-eligible and are suppressed from automatic referral allocation, billing reminder queues, and credit-limit disconnection queues. A finite period resumes at the next valid plan cycle; an open-ended period has no next billable date.
- Reconnection settlements are stored as sanitized audit history on the branch/account disconnection decision. A stopped interval never creates catch-up cycles. The previous balance remains a separate ledger component and is either retained, written off once, or deferred into an exact cent-balanced schedule. Admin may create a separate remaining-days proration, a separate complete-plan full-month charge, or no immediate charge; either immediate charge advances the following prepaid first-day or postpaid month-end regular cycle so it cannot duplicate the selected month. Pending-payment settlements create no charge, count only new collected-payment entries, protect those activation payments from deletion, and rebuild the selected charge plus next billing/due dates from the actual activation day if payment arrives later.
- Payment confirmation proof paths remain rooted at shared `public/uploads` through `core/runtime/paths`.
- `backend/payment-confirmation-queue-store.js` supports the default JSON store key `payment_confirmation_queue` and optional MySQL table, including submitted payment date and SHA-256 screenshot hash. New submissions always start as `pending`; duplicate images and pending/approved references are rejected.
- Screenshot analysis metadata is stored as `proofAnalysis` in JSON and `proof_analysis_json` in MySQL. `backend/gcash-screenshot-parser.js` adapts the GCash label strategy from AJAbanto's MIT proof of concept to the Node runtime, runs Tesseract.js with packaged English trained data, serializes OCR work through one lazy worker, and caches recent image hashes to avoid duplicate recognition between preview and submission. Local OCR starts with a block-layout pass, supplements incomplete or low-confidence reads with automatic layout and then sparse-text recognition when key fields remain missing, combines the passes before parsing, normalizes a common `+163` OCR error to the Philippine `+63` number, and rejects status-bar text as a recipient name. `backend/gcash-vision-ai.js` is disabled by default; `GCASH_VISION_AI_ENABLED=true` plus an HTTP(S) `GCASH_VISION_AI_ENDPOINT` and `GCASH_VISION_AI_MODEL` opt into an OpenAI-compatible chat-completions endpoint, with optional `GCASH_VISION_AI_API_KEY`, provider label, timeout, and OCR-confidence threshold. It sends screenshots externally only after that opt-in, caches normalized results briefly, and never persists an endpoint, credential, raw provider response, or screenshot copy.
- Hybrid analysis never overwrites a locally read field. Vision AI fills only missing fields, records per-field `local_ocr`, `vision_ai`, or corroborated provenance, and raises visible conflict warnings when it disagrees. AI-only contradictions do not become an automatic approval blocker; imported history, locked customer submission fields, immutable transaction allocation, and explicit Admin approval remain authoritative.
- `backend/gcash-pdf-parser.js` uses `pdfjs-dist` to read both credit and debit text rows from the official encrypted statement layout. `backend/gcash-transaction-history-store.js` stores batch metadata, normalized transactions, audited remarks, and claimed/posted allocation groups in the storage-aware `gcash_transaction_history` app store, so JSON and MySQL modes share the same branch-scoped contract. Missing debit/credit values remain null rather than being converted to zero. PDF hashes identify repeat uploads, while normalized exact references are the branch-wide uniqueness key across every PDF. Existing references—including rows whose incoming details differ—are retained unchanged and counted as skipped so unrelated new rows still import; a claimed or posted group cannot be reassigned to a different allocation signature. Each group retains one to three customer/account, exact amount, server-derived current billing month, payment-entry associations, current posting date, original imported transaction data, claiming Admin/time, and posted time; legacy single-allocation fields are sanitized into the same group representation. Recipient labels are derived for display without replacing the original number.
- `backend/payments.js` exposes the internal idempotent approved-payment writers used by proof approval and direct imported-history posting. The batch writer validates one to three distinct allocations totaling the imported credit, supports both JSON and relational payment storage, rejects normalized reference/OR-number reuse before insertion, assigns canonical entry numbers in relational transactions, records the Admin and GCash source on each entry, and commits all entries together before running existing paid-service/prepaid refresh effects. Identical retries return the complete stored group; partial pre-existing groups fail closed.
- `backend/payment-confirmations.js` keeps approval/rejection/new-proof requests staff-only. **Request New Proof** changes only the queue status to `needs_new_proof` with customer-visible instructions. For GCash, **Approve & Post** requires an independent imported-history match, immutable submitted amount/reference, no reliable OCR contradiction, and explicit Admin confirmation that the transaction belongs to the displayed customer/bill. The official transaction is claimed for exactly one submission/account, the idempotent ledger credit and queue review are posted, and the allocation is finalized with the payment entry; only that path triggers receipt data, prepaid extension, and paid-service/MikroTik refresh behavior.
- Payment backups remain rooted at `data/payment-backups`, and Cloudflared configuration remains rooted at `.cloudflared/config.yml`.
- Depends on Customer Management for customer identity, plan assignment, referral state, and archive visibility.
- Depends directly on the migrated Network backend for RouterOS connectivity, PPPoE normalization/auditing, and service enforcement; Network consumes Billing plan-profile intent.
- Collector submits payments, approvals, and remittances against Billing records.
- Customer App submits payment confirmations and displays customer balances/statements.
- Business profile and integration settings are Admin-owned shared inputs.
- Payments, Payment History, Payment Breakdown, and the Customer Management customer list require `/api/payment-records` as their shared billing read source. Missing/invalid summaries display a Billing unavailable state; browser billing fallbacks are not executed.
- The Payments breakdown table remains display-only: it formats version 2 `billingSummary.rows` but does not calculate charges, balances, advances, or statuses in the browser. Its **Add Payment** action reuses the existing locked-customer payment form and `/api/payments/:accountNumber` write path; adjustment, plan-change, and service controls remain on the existing full page.
- Manual Billing payments already pass through `/api/payments/:accountNumber`, which validates duplicate references/fingerprints and uses a database transaction in relational mode. Collector capture remains a separate Collector-owned write contract and is not changed by this read-model cutover.
- Payment History GCash reconciliation uses the official history store's normalized branch reference and immutable allocation claim/finalize contract. New matching entries keep the existing Excel-import ledger shape and service-refresh behavior; the workflow does not call the direct current-month posting writer and does not recalculate or edit Payment Breakdown rows.

## Known risks and follow-up

- Billing and payment files are large and contain cross-module network/service effects; behavior changes require focused financial regression coverage.
- Scheduler changes can create duplicate or incorrectly timed charges; test Manila-time and idempotency behavior.
- Payment numbering and relational transactions are high-integrity paths.
- Shared receipt, statement, route-mount, and static-delivery logic in `server.js` requires Integration Codex locks.
- Repository-root backend aliases must not be recreated; scripts and cross-module consumers use canonical paths.
- Expand automated billing-cycle, relational transaction, and disconnection-policy tests before changing behavior.
- The imported email PDF is stronger independent evidence than a screenshot but is not a live GCash settlement API. Admins must verify that the statement email/file is genuine and still make the final approval decision; no screenshot or parsed statement row automatically posts a ledger credit.
- OCR accuracy depends on screenshot resolution and GCash layout changes. Missing or conflicting fields are warnings and never silently become confirmation; the customer may still submit unreadable evidence for manual review.
- Enabling Vision AI sends unclear customer screenshots to the configured external provider. The operator must choose an appropriate provider, protect its API key, review retention/privacy terms, and keep the fallback disabled when external processing is not acceptable.
